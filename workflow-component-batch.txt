BATCH MODE（攒批）— only when the human declares a batch ("这批攒批 /
系列处理 / 大系列"); never on by default. Single-issue work keeps the
per-issue push rhythm.
- TICKET ENTRY CONTRACT（票面契约 —— every ticket, batch or not）: RFA = the
  ticket needs NO user in the loop AND has NO open decision. That TEST is the
  label's: its definition lives in the tracker's `docs/agents/triage-labels.md`
  (the expansion checklist and the stock re-check stay with the tracking side).
  What this contract pins is the ticket BODY — five things written down before
  the label goes on:
  (1) the write-domain whitelist (including "may touch a same-family file
  when the criterion requires it"), (2) the criterion's form (what the assertion
  compares against), (3) the acceptance reading (exact command + expected
  output), (4) the closing rule (which ticket(s) it closes, and who may close),
  (5) the push checkpoint. A ticket that cannot pin one of the five is RFH, not
  RFA.
- REQUIREMENT CONSERVATION & WIRE-OFF (#148 — every ticket that splits,
  defers or hands off an approved requirement): each approved requirement
  maps to exactly ONE lawful destination — delivered in THIS ticket / taken
  by an EXISTING ticket whose ACs carry it / a goal change the human
  explicitly authorized (a gate-3 L2, never the implementer's call). An
  unmet original goal stays UNFINISHED — disclosure is not delivery, and
  closing sub-tickets never proves the whole capability works. A handoff is
  BIDIRECTIONAL or it does not exist: the sending ticket names the receiving
  ticket AND the receiving ticket's ACs take the same wire — "a later ticket
  handles it", a missing receiver, or a receiver that never took the AC all
  FAIL. Blocked-by edges are scheduling order, never a verified connection.
  Criteria + counter-examples: docs/agents/issue-tracker.md (需求守恒与接线
  移交); review consumes it at docs/code-review-brief.md §2.
- RETIREMENT EVIDENCE BAR (#149 — every ticket that retires, deletes or
  disables a module or capability): "no callers", "no data", "not yet used"
  are LEADS, never verdicts. Classify the break FIRST — producer missing /
  consumer missing / goal cancelled / superseded by a same-duty
  implementation — against the approved goal and the original capability
  chain. Retiring a module that still carries an approved duty needs a
  POSITIVE basis (the human-authorized cancellation record OR same-duty
  coverage evidence) plus impact scope and uncovered duties listed; a
  product-capability cancellation is a gate-3 L2, and high-risk actions
  (drop tables, delete data) are never dressed up as cleanup. Normal cleanup
  keeps flowing: provably duty-free redundancy, real unreachable branches
  and internal duplication need no extra confirmation round. Criteria +
  counter-examples: docs/agents/issue-tracker.md (退役判据); review consumes
  it at docs/code-review-brief.md §2.
- RFA is not "fully specified on paper": if implementing it needs the human to
  pick a direction, supply a credential or environment, judge a real-UI run, or
  be present while it is verified, it is RFH however well the body is written.
- A REAL open decision found at runtime — mutually exclusive ACs, a destructive
  step, a write outside the declared scope, a criterion that contradicts the
  measured repo — DOWNGRADES the ticket to RFH and STOPS. Ask-then-continue is
  the failure this rule forbids. What counts as real is exactly that list plus
  the enforcer's high-risk list; everything else is routine — decide it and put
  one line of "decided X because Y" in the delivery comment so the human can
  audit it afterwards.
- CONFLICT ZERO（四类冲突归零）— at triage / grill close-out, four faces, all
  four read before the RFA label goes on:
  - ① inside the ticket: the ACs do not contradict each other and their
    arithmetic is feasible;
  - ② ticket vs measured reality: the symptom / root-cause section was
    re-measured on HEAD (one command + its reading, D9) or is marked "not
    measured, assumed";
  - ③ DOCUMENT vs measured reality: `git grep -n <the ticket's keywords> -- docs/
    *.md`, every hit judged "still true" or "stale, this ticket supersedes it";
    a document that contradicts the ticket is either fixed or explicitly
    overridden inside the ticket;
  - ④ ticket vs tickets: duplicates, dependency direction and batch assignment
    checked against `gh issue list`, and no write-scope or criterion overlap
    with the other members of its batch.
  One unread face → NOT RFA. Each face's disposal (resolved / decided /
  explicitly declared) is written INTO the ticket, never left in the chat.
- No decision-pushing wording in a ticket body, and no line admitting the ticket
  still needs a human decision (that admission IS an open decision → the ticket
  is RFH, not RFA). Each such phrase IS an unread conflict face. The unambiguous
  token lists live in exactly TWO places — the tracker's procedure
  (`docs/agents/issue-tracker.md`, always) and, where the repo ships one, a
  matcher (this repo: `scripts/triage-check.mjs`; without one, the same list is
  read by hand). This text POINTS at them and never re-enumerates: a second
  enumeration is precisely the drift these rules exist to prevent. The
  contextual half (a bare "?" hung on a decision, "或" as an option list, 建议
  in the "要不要做" sense) stays a human read, declared as such in that doc.
- BATCH DECLARATION PRE-AUTHORIZATION LIST（批宣告预授权清单）— the declaration
  is the license for autonomous execution, and it authorizes exactly four
  things:
  - WRITE SCOPE: the declared write-domain whitelist + "a same-family file when
    the criterion requires it" + the ticket's own evidence artifacts. A write
    outside it is a real decision → stop.
  - CREATE TICKETS: in-batch you may CREATE tickets for discoveries outside the
    ticket's scope（只建不关 — never close them in-batch). TICKET-FACE DOUBLE
    PRECONDITION (#51 Q9′ / #135 — a ticket-face action `gh issue create /
    comment / edit` runs confirmation-free ONLY when BOTH hold; either failing
    → NOT pre-authorized → the ⚠ gate face, stop and ask): ① SCOPE — the
    target ticket is a batch member OR sits on the registered 批外票清单
    (registration is the HUMAN's call; a self-registered ticket has no
    authorization basis); ② CONTENT — the body has already passed the
    PRE-PUBLISH privacy scan (`node scripts/privacy-scan.mjs --text-file
    <draft>` exit 0 — same judgement as the repo scan; missing/empty input
    fails LOUD exit 2, D47). `gh issue close` / re-labelling write no body →
    only ①. FAIL-CLOSED: no exit-0 evidence = condition unmet — "scanned and
    clean" must be evidence, never an assumption. Residual limits recorded
    (#51 Q9′): content clean ≠ no side effect (watcher emails cannot be
    recalled); the scanner only knows KNOWN shapes — the digest backstops the
    rest. Judgement entry: `ticketFacePrecheck()` in `workflow-enforcer.mjs`
    (pure function; positives/negatives pinned by V39).
    Read the labels back
    after creating: `gh issue view <n> --json labels --jq '[.labels[].name]'` —
    exactly one category (bug / enhancement) + exactly one state (one of the
    five roles). A ticket with no state is invisible on every state-filtered
    surface (#126 / #127 were built that way).
  - CLOSE TICKETS: the confirmation mode of closing is chosen AT DECLARATION
    TIME and recorded in the batch state — (a) per-ticket confirm (report →
    human confirms → close; the default), (b) in-batch pre-authorization (a
    finished member is closed without asking, on the batch-end review), or
    (c) batch-end once (nothing closed in-batch; the summary gate closes the
    whole membership). If the declaration names no mode, (a) applies AND the
    declaration prints the loud line 「closing mode not declared — per-ticket
    confirmation」 (D47: absence is loud, never the convenient default).
    Comment-closing is still an external action (D21) — the authorization covers
    the DECLARED members only and NEVER carries into another batch.
  - PUSH: once, at the batch end, through the summary gate. Never per ticket.
- STYLE PREFERENCE LAYER（风格偏好层, #49 — user preference, NOT a fifth
  authorization column）: the confirmation TIMING of out-of-batch Bucket-B
  tickets rides a user style preference file OUTSIDE the repo
  (`<DSH_HOME>/batch-style-preference.md`; its SHAPE lives in
  `docs/batch-state.md`「风格偏好层」— the single source for the shape —
  and the tier ENUMERATION is pinned in `workflow-enforcer.mjs`
  `STYLE_PREFERENCE.tiers`; its VALUES never enter the repo). No preference
  file → the `保守` tier (the default: everything stays as declared —
  in-batch four columns as declared, out-of-batch tickets confirmed one by
  one). `标准` = `保守` + tickets registered in the batch state's 批外票清单
  may be re-labelled and closed without per-ticket confirmation (the three
  evidence elements required); registration is the HUMAN's call (at the
  declaration, or an explicit later addition) — the agent never registers a
  ticket into 批外票清单 itself, and a self-registered ticket has NO
  authorization basis.
  The tier names are an enumeration of exactly two (`保守`/`标准`); per-item
  exceptions ride `加:` (allow beyond the tier) / `减:` (deny within it),
  each with a one-line reason and a date. BOTH tiers exclude push. Like
  in-batch pre-authorization, the preference changes WHEN a confirmation
  happens, never the NATURE of the action — out-of-batch closing is still
  an external action (D21). The preference file is HUMAN-write-only: the
  agent may transcribe exactly the version the human approved VERBATIM,
  then echo the written file in full + its absolute path, and treat it as
  read-only from then on (Q4; same discipline as D51's "only touch what you
  yourself created"). First batch declaration with no preference file →
  ask ONCE whether to record it (the same `batchDeclare` face, zero new
  hooks); a human stating an authorization preference anywhere with no file
  on record → propose recording it once; never ask otherwise (Q5).
- CLOSE-OUT STEP — BEFORE A BATCH IS DECLARED（收口步）: classify the open
  backlog (series / needs-triage / ready-for-human / standalone), MERGE the
  same-family tickets that one session or one edit would close together, and
  only then allocate batches (capacity 10–15 tickets, a candidate queue of
  5–10 padded at the tail — a blocking gap fills from the tail). When counting "ready to start",
  DROP the tickets that are already DONE but not yet closed — a frontier that
  counts them overstates the queue (B-batch reading, 2026-10-19: 28 vs a true
  25). Record the close-out in the batch state (the classification line + the
  merge decisions) so the next session reads it instead of re-deriving it.
- EXPLICITLY NOT GUARDED (D15): tickets live on GitHub and the local suite
  NEVER queries the tracker. The ticket-side faces above — labels, close mode,
  conflict-zero declarations — are verified at the batch-end review, not by a
  guard. Guards cover only what is decidable in-repo: this body verbatim, the
  batch-state shape, the frozen fixtures, the bundle, and the enforcer's
  injection text.
- Batch = the set of issues the human declares (usually one series,
  e.g. #503 T1/T2/T3, or a to-tickets feature's ticket group). The
  declaration must name the members and the end point (last ticket).
- Inside a batch: work each ticket → local commit + local verification
  (L1/L2/clippy/fmt/code-review) → NO per-ticket push. Closing an issue
  may precede the remote CI (based on local verification + code-review);
  the remote CI is confirmed once at the batch-end push. In-batch closing
  is the THREE-STAGE CLOSE: local gate chain all green + code-review both
  axes pass → the batch-state Progress row (three evidence elements) →
  the close comment with the fix + verification evidence → `gh issue
  close`. Interaction with the enforcer's close face (judged at wave-1):
  the real `gh issue close` call still arms the fresh-subagent spot check
  (O5) — in-batch closing rides the declaration's closing mode and never
  bypasses that nudge or the three evidence elements.
- ONE TICKET PER SESSION STILL HOLDS (human-mandated): batch mode never
  changes the session grain — each ticket gets its own implement
  session (one ticket + its verification), handing off through
  batch-state.md. Never chain tickets inside one session on the grounds
  that they are "same batch / related" — the gate-5 fold-in conditions
  are NOT relaxed by batch mode. The batch-end wrap (summary → human
  confirmation → push) is done by the last ticket's session as its
  closing step, or by a dedicated wrap-up session; it is not a ticket.

- WAKE ORCHESTRATION (#163 — L2 first version = orchestrator polling;
  #50 evidence base): an unattended batch orchestrator keeps a child
  session's turn ALIVE by polling. The wake/deliverable/metering logic
  is canonized in `lib/autonomy-orchestration.mjs` (single source; the
  evaluation consumer `evals/autonomy/runner.mjs` imports it and carries
  no embedded copy). Mechanics, all #50-measured: judge the turn by the
  event stream's `turn/end`-after-`turn/start` seq order — NOT
  `projections.running` (its shape lies mid-turn); while
  `subagentCatalog` shows subagents in flight (`continuable` entries
  with `subagentTiming.settledMs === 0`), a `turn/end` is NOT treated as
  death — hold for the settle-and-resume (both measured chain breaks
  were exactly this shape: the session ended its turn waiting on
  parallel code-review subagents), the overall timeout stays the
  backstop; once idle past a 6-minute grace with no subagent in flight
  and the deliverable criteria unmet, ONE nudge fires (criteria faces,
  #50 verbatim: A group = commit + evidence/green.txt +
  .eval/{delivery-comment,decision-gate}.md; relay hop 1 = handoff doc
  on disk; relay hop 2 = new commit — a nudge never covers a generic
  "not done"); after MAX_NUDGE=1 it stops and reports honestly.
  Metering is first-class (#50 retro candidate 4): every
  orchestrator-proxied action — nudges, human relays — is counted and
  carried in the conclusion; an autonomy reading never hides the
  fallback inside implementation details.
  Closing-step seam (#160: full-auto ends at the closing step): delivery
  is automatic; push/close-ticket and other D21 external actions STOP
  and ask. When the session asks (`ask_user_question` pending with no
  later turn/start), the orchestrator RELAYS the question through its
  `onAwaitingHuman` channel, injects the answer as the next prompt
  (metered as a relay; one relay per pending question — never a
  re-inject storm), or with no answerer stops at awaiting-human
  carrying the question verbatim instead of letting the overall timeout
  truncate it (the #50 chain3 break).
- HANDOFF WRITING RULES (#159): a handoff document carries THIS SESSION'S
  facts + pointers — never a restatement of repo discipline. AGENTS.md and
  docs/agents/* are the single authority; a cached copy of a rule drifts
  the moment they change (a real handoff carried 11 restated rules — most
  already had an authoritative home). Three rules: (a) write only what
  THIS session produced — commands actually run and their results,
  environment anomalies, faces not verified (or not verifiable here),
  implementation judgments the ticket did not specify, with the reason;
  (b) every discipline is a pointer ("见 AGENTS.md / docs/agents/issue-tracker.md 等"),
  never the rule text; (c) the handoff ends with a 「未验面」 section.
  Skeleton (5-10 lines, expand each heading with session-local facts only):
  ## 现场事实（本会话产生） — commands run + results, anomalies, blockers;
  ## 票面没写的实现判断（+理由） — decisions only this session knows;
  ## 未验面 — what was not run / not verifiable here and why;
  ## 指针 — discipline pointers (AGENTS.md / docs/agents/issue-tracker.md 等), not
  restated rules.
  The appended 环境快照 git values and 产物清单 sha256 entries are machine-filled by
  the handoff tool at generation time (git probes / hashing over the declared artifact
  paths, #168) — the parent session never hand-fills them, and the manifest section
  exists only when artifacts are declared (no placeholder lines). Directed handoffs
  whose credential is a ticket number additionally get a 票面回读 section: the tool
  reads title/state/labels from the tracker at generation time (#172) — transcribed
  ticket fields lose to that section, and fields it cannot know are marked 生成后漂移
  (the child re-reads the tracker; a failed read is marked loudly, never downgraded
  to the transcribed values).
- Batch end: after the summary gate, push all commits in one go; remote
    CI all-green is the completion gate — red means unfinished batch work,
    bisected by commit boundary to the offending ticket, fix and re-verify.
- SANDBOX BATCH MODE (sandcastle; opt-in — only when the human asks for
    sandboxed/AFK parallel ticket runs, e.g. "沙箱批跑"): the main session
    ORCHESTRATES, sandboxed DSH-headless workers EXECUTE; human judgment
    at the edges (audit before launch, PR/digest review after), agents in
    the middle.
    (a) The orchestrating session is a dedicated wrap-up-style session —
    it never edits ticket code inline; one-ticket-per-session governs the
    implement grain, workers are external executors, not sessions.
    (b) TICKET AUDIT BEFORE LAUNCH (input quality gate): a ticket enters
    the queue only with a recorded audit — AC decidable (what "done"
    means is checkable), touch-set declared (expected file set), the
    proving verification command named (exact test/lint), forbidden-path
    scan clean (migrations / money-path / governance semantics → demote
    to the daytime batch lane), size estimate sane. Audit fails → the
    ticket goes back for spec rework, never launches on vibes. Mechanical
    pre-check: `.sandcastle/audit-ticket.mts` writes the audit record;
    the orchestrator judges what the machine cannot.
    (c) TOUCH-SET CHECK across the launched set: overlapping tickets are
    serialized or merged into one — never run in parallel.
    (d) Y-LANE SHAPE (audit-passed tickets): one podman sandbox + one
    run per ticket on `branch` strategy; the merge gate is the
    ORCHESTRATOR-run verification exec in the same sandbox (the exact
    command the audit named — never the worker's self-report); a big
    diff passes a simplify pass before that gate. Merge serially in
    waves (3–5), rebase onto master one ticket at a time; a
    conflicted/rejected ticket returns to its sandbox for one rework run
    or goes to Bucket A. Every finished ticket persists a checkpoint
    (state file: SHAs + verification output) and every worker runs under
    a wall-clock watchdog — unattended batches resume from the
    checkpoint, never from zero. Batch end still = one push through the
    summary gate (Actions-minute economy, ADR-0002); PR-per-unit
    (`--pr`) only where CI budget allows.
    (e) Every sandbox launch is an EXTERNAL-ACTION GATE event (enforcer
    matches `sandcastle`/`run-ticket`); the batch-end push still goes
    through the summary gate. (f) Ticket exit evidence = audit record +
    commit SHAs + verification exec output + the sandbox run log;
    "worker said done" alone closes nothing. (g) WORKER CONTEXT: every
    worker task injects the project's principles/gotchas digest (from
    CONTEXT.md/AGENTS.md/ADRs) before the ticket body — workers read
    before acting. (h) CLOSE-OUT AUDIT: wave merges go through the
    `ticket-audit` skill (adversarial checklist, EXEMPT from ponytail —
    a lazy auditor is how bad merges ship); ponytail rides with workers
    (worker-context) and activates in main sessions only on explicit
    invocation. Scaffolding: preset `sandcastle/templates/` — see
    README「沙箱批跑」and ADR-0003.
- OUT-OF-TICKET DISCOVERY — THREE-WAY DISPOSAL（票外发现三分法）: the
  COMPLEMENT of gate 3's L0/L1/L2 — the tiers grade DECISIONS, this
  grades DISCOVERIES, and together they cover every in-batch reason to
  stop and wait. A discovery that is itself an open DECISION grades
  through gate 3, never through this disposal:
  (i) solvable on the spot → same-family fold-in (gate 5's three
      conditions: the current ticket is done, the link is stated, the
      context evidence shows a healthy window);
  (ii) not blocking the current step → file the ticket, continue the
      current one;
  (iii) blocking → file the ticket, archive the current ticket's WIP by
      the conflict-aware jump protocol below, jump to the next member —
      the batch never stalls on one ticket (the filed ticket waits for
      the human; the batch does not).
- ISSUE DISCIPLINE (anti-laziness; every discovery is an audited event):
  any bug/finding first lands in the issue tracker — create a new issue
  or update the matching one — THEN process, THEN update the issue again
  with the fix and its verification evidence ("update issue → process →
  update issue"). Never silently fix inline, never silently ignore.
  - Bucket A (blocks the current ticket): disposal (iii) above — file it,
    archive the WIP by the jump protocol, jump to the next member.
  - Bucket B (non-blocking, outside the batch): land the issue → fix
    with full verification → update the issue → continue the batch.
  - Bucket C (found at batch verification, e.g. red CI): locate the
    issue/commit → update the issue → fix → re-verify → update the issue.
  - Any plan/scope change follows the same "update issue → process →
    update issue" loop.
- CONFLICT-AWARE JUMP PROTOCOL (修正案 — replaces disposal (iii)'s naked
  "stash and skip", whose hidden premise — the WIP diff and the next
  ticket's writes are disjoint — fails exactly when blocking is CAUSED by
  a write conflict; the three failure shapes it prevents: an unclean
  archive that tangles the next ticket's start, silent WIP carry-over
  that pollutes the red-CI attribution, a stash-pop conflict detonating
  at batch end with the ticket's context lost): BEFORE archiving, run the
  intersection check — the current ticket's `git diff` (including
  staged) against the next ticket's declared touch-set. Disjoint →
  archive and jump (the original path). Intersecting → BRANCH PARKING:
  `git switch -c wip/<票号>-<slug>`, WIP-commit on the branch, back on
  the main line open the NEXT ticket's branch — #103 one-ticket-per-branch
  as the IN-BATCH shape: the WIP never crosses into the next ticket's
  working face, conflicts surface at the merge boundary where they are
  attributable, not in a stash; in-batch zero-push is unaffected (the
  branches are local). The state surfaces carry the FULL handoff —
  branch name, WIP commit, the conflict point, the resume condition
  (batch-state.md / .scratch/progress.md / the goal + task list;
  updating one ≠ the others are updated). Batch-end CI semantics are
  unchanged: CI runs the main line's committed work only, branch WIP is
  not in it, and the red-CI bisection stays unpolluted. Resume is
  EXPLICIT: continue on the branch or merge it back, conflicts resolved
  at the branch boundary — never "redo from memory on the main line".
- BATCH-END SUMMARY GATE: before the batch ends, the summary must list
  EVERY issue from the process (A/B/C, created and updated); the push
  happens only after the human confirms that summary. The batch-end push
  is therefore NOT pre-authorized — it is the normal report → confirm →
  push flow, with a mandatory full-issue summary first. Every ticket
  line in the wrap summary carries the three evidence elements (command,
  exit code, evidence path — the test output itself counts); a line
  missing any is BLOCKED, not done —
  this adds evidence, it does NOT relax the CI confirmation (DONE and
  the batch-end gate keep their full force).
- AUTONOMY DIGEST (#49 Q6 — no new artifact, the wrap conclusion IS the
  carrier): the wrap conclusion carries one fixed-format digest line per
  autonomous action taken outside the declared batch authorization
  (Bucket B / preference-tier moves):
  `自主 <动作> · #<票号> · commit <sha> · 证据: <命令> → exit <code> · <输出路径>`.
  In-batch actions are NOT re-copied into the digest — the batch-state
  Progress rows already carry the three evidence elements; one pointer
  line covers the batch. A digest line missing its evidence is marked
  `未验证` and ESCALATED to an exception (D47), and a separate
  `⚠ 无授权依据的动作` section lists every autonomous action that had no
  authorization basis — OVERREACH ACTIONS GO FIRST in that section (置顶,
  #135): an action that lands in NONE of the three authorization bases
  (「routine 白名单」∪「批内预授权四列」∪「风格档 + 例外清单」— mechanical
  judgement `isOverreach()` in `workflow-enforcer.mjs`) is overreach, and
  overreach = 收回授权, NOT a rollback: run the THREE-STEP STOPGAP
  (`OVERREACH_STOPGAP`) — ① STOP: no new tickets, no push (every ⚠ gate
  action asks again); ② DEGRADE: the rest of THIS session runs on the
  `保守` tier (local reversible work only; changing the tier back is the
  HUMAN's move, #49 Q4); ③ CHECKPOINT: WIP lands — branch + a batch-state
  checkpoint line naming the sha (`checkpointLine()`) — and the overreach
  action goes into the digest's `⚠ 无授权依据的动作` section FIRST.
  NO AUTO-REVERT (`OVERREACH_STOPGAP.revert === false`): already-done
  actions stay for the human to adjudicate — a revert would itself be a
  write whose only justification is the same judgement that just misfired
  (#51 Q2=A). Step-by-step assertions: V40.
  Overreach/quality readings (#49 Q7 — no evaluation
  rig): at each batch close-out, record one line — (count of
  `⚠ 无授权依据的动作`) ÷ (total autonomous actions in the batch);
  completion quality reads the existing O5 fresh-subagent spot check
  after ticket closure; three batches' worth of these lines is the
  production data AC③ asked for. Distortion readings (#163 batch-end
  audit slot — async): a batch that ran auto-handoff hops records ONE
  more line at close-out — per hop, the manifest re-verification

- PUSH/COMMIT-TRIGGERED RETRO (mandatory, not a suggestion) — the batch's
  richest retro material is the batch itself: many tickets, many
  sessions, usually rework and handoff loss. Two obligations, keyed on a
  REAL push or a REAL commit (a commit arms the LANDING face only):
  - PER-TICKET PUSH OR COMMIT → WRITE CANDIDATES TO DISK: on a real push
    or a real commit, run this session's retro at once and write the
    candidates to .scratch/retro/<batch>-<session>.md — content = candidates
    (ordered by severity) + evidence (command / output) + source (session id /
    ticket number) + why it was not landed. `<session>` is the session id's
    SHORT form — the 8-hex segment after `session-` (NOT the id's first 8,
    which would be `dsh-matt`). CANDIDATES ONLY, never
    land them (landing is still the human's call, D22/D27). Writing a
    local candidate file is NOT an external action (D21 covers push /
    closing / creating issues), so it is CONFIRMATION-FREE and
    NON-BLOCKING: keep going, never stop the wrap to ask. Re-running in
    the same session overwrites the same file (idempotent). A COMMIT arm
    is per-session: once .scratch/retro/*-<session token>.md exists, later
    commits (including --amend) stay silent — pure existence, no
    batch-state parsing.

    every landed file of the same batch, DEDUPE AND MERGE (the same
    problem recurring across sessions is merged with a COUNT — that
    merge is the whole point of aggregating), order by severity, and
    present ONCE to the human, every line tagged with its source ticket
    number / session. Never re-read the whole batch history at batch end
    — the landed files replace that. Then wait for CI green (or the push
    itself when the repo has no CI), and write the completion marker
    `retro: done @ <commit>` into .scratch/batch-state.md. That marker says
    the batch-end retro has RUN — it is NOT what keeps the presentation to
    once per batch, because it is written BEFORE the batch-end push, so
    every later session of the same batch would aggregate again. Two
    markers, two facts: after actually PRESENTING the aggregation, APPEND
    to the registry file `.scratch/retro/.aggregated` one line carrying
    THIS batch's id (`<batch id> aggregated @ <date>`; the id is the

    ENTRY is the CROSS-SESSION suppressor for THIS batch (每批至多一次
    constrains the PRESENTATION, never the material): a later session of THIS batch does NOT aggregate
    or re-present, while a NEW batch stays due (the check is "the current
    batch id has an entry", never mere file existence — #140). A later

    re-present; it still runs its own retro and LANDS its candidates, so
    no material is lost (不静默丢素材). Both markers are written by YOU

    batch-state shape is

    is the (toolName, argv) pair — the tool layer plus the command layer
    of a shell tool, judged at the COMMAND POSITION (`git push` = landing
    or aggregation; `git commit` = LANDING ONLY — it never aggregates,
    and it is per-session: once the session's candidate file exists, later
    commits are silently consumed by pure existence, no batch-state parsing).

    false trigger costs more than a missed one (a wasted retro run plus

    stays narrow and never grows a keyword fallback.
  - FALLBACK — NEVER DROP MATERIAL SILENTLY: the injection rides the next
    prompt assembly, so a push OR A COMMIT that is a session's LAST action

    forbids.
