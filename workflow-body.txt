@@ main-flow
MAIN FLOW — idea → ship:
1. Sharpen — only when the shape is genuinely undecided (a decision
   still open): run the grilling interview (load the `grilling` skill)
   and keep the `domain-modeling` vocabulary; in a working directory
   prefer the stateful /grill-with-docs (CONTEXT.md + ADRs), without
   one /grill-me. A spec already decided goes /to-spec → /to-tickets; a
   decided shape goes straight to /implement. In the grill, ask only
   what the CURRENT round can settle: a question whose answer depends
   on an in-flight fact or a subagent that has not reported yet is not
   this round's — park it and keep going (frontier).
2. Prototype detour. When a question needs a runnable answer (state,
   business logic, a UI to see), propose /prototype and bridge it with
   /handoff in both directions, folding the answer back into the idea.
3. Build. Multi-session effort → /to-spec, then /to-tickets (tracer
   bullets declaring their blocking edges, worked blockers-first), then
   one ticket per fresh session via /implement. Single-session →
   /implement right here. /implement drives /tdd internally (red→green)
   and closes with /code-review (Standards + Spec) before committing.
   When the work goes up as a PR, /pr (model-invoked: the agent
   reaches for it whenever it writes a PR body) shapes that body —
   the smallest visual that shows the change, before/after evidence
   that it works, and a one-way/two-way door call.
4. Retro. After the build lands — especially one that went sideways —
   /retro closes the loop: it looks back over the session and suggests
   changes to the agent's ENVIRONMENT, not the code (navigation
   pointers, automated checks, the coding standards /code-review
   enforces, steering files, tooling), so the next build starts from a
   better environment.
@@ workflow-enforcement
WORKFLOW ENFORCEMENT — seven hard gates; the workflow-enforcer plugin
injects their details and high-risk-action reminders per request.
Violating them (silent skipping, deciding for the human, coding without
a plan, external actions without confirmation) is the one behaviour the
human will push back on:
1. ENTRY ROUTING — classify the task by SHAPE and SAY which flow you
   start. Shape undecided (a decision still open) → the grilling
   interview (then to-spec → to-tickets → one implement per ticket);
   spec decided, tickets still to cut → /to-spec → /to-tickets; shape
   decided → /implement directly. Trivial work may skip the ceremony —
   say why in one sentence.
2. IMPLEMENT GATE — no code change beyond a trivial edit without
   planning artifacts (CONTEXT.md decisions, docs/adr/, spec/tickets).
3. DECISION BOUNDARY — real decisions are never made for the human; the
   gate face is unchanged — but GRADE before interrupting (attention is
   the scarcest input: every interruption costs the human a reload).
   Grade L0 → L1 → L2 in order; one unmet condition is out; ambiguity
   grades UP — ask rather than self-decide, never the reverse.
   L0 SELF-DECIDE — all four hold: git-revertible, no external side
   effects ∧ inside the ticket's declared scope ∧ matches an existing
   repo pattern (no new pattern) ∧ touches none of the seven gates →
   decide it, RECORD each one (a "decided X because Y" line in the
   ticket's decision log), and list the L0 items at the phase boundary
   for the human's one-glance audit. L0 is hedged, not exempt: the audit
   + running the gates green yourself before handover + grading a
   high-blast-radius self-decision up to L1 even when reversible.
   L1 BATCH — the human's input is needed but does NOT block the current
   step → park it, keep working, ask the parked batch ONCE at the phase
   boundary (an unparked L1 is a lost question — never silently drop it).
   L2 ASK NOW — a blocker (this step cannot continue) / irreversible or
   external side effects / recovery STOP-and-ask / scope expansion, AC
   rewrite, triage three-way → ask and wait (the classic form of this
   gate; destructive or high-cost steps are here). FOUR CLASSES NEVER
   GRADE DOWN to L0/L1 — always L2: D21 external actions (gate 6);
   recovery's STOP-and-ask; the privacy face (personal/machine
   environment never enters the repo); scope expansion, AC rewrites,
   triage three-ways (gates 5/7). L2 asking quality: ONE decision per
   question (parallel tickets ask serially), always with 前因后果
   (background: where the question comes from / the key facts / each
   option's substance and cost / ties to prior decisions) — the grill
   contract's four-piece block stacks, no new format. Read
   AGENTS.md/CLAUDE.md early.
4. PHASE DECLARATION — one-line phase opener at every boundary
   (grill → spec → tickets → implement → review, /handoff). Starting a
   flow skill (triage, to-spec, to-tickets, implement, code-review…) —
   or the grilling interview — requires loading its SKILL.md first; never
   run the flow from this map's one-liner alone.
5. ONE ISSUE PER SESSION — one issue plus its verification; hand the
   rest off, never continue inline. A related ticket may fold in only
   when: the current ticket is done, the link is stated, and the
   measured context evidence shows a healthy window. Continue is a
   phase-internal rule — it never extends to the next ticket. BATCH MODE
   (below) does NOT relax this: one ticket per session, batches span
   sessions via batch-state.md.
6. EXTERNAL-ACTION GATE — external/destructive actions (push, PR/issue,
   publish, DB reset, rm -rf, force-push): report, then WAIT for
   confirmation. BATCH MODE (below) makes the batch-end push flow
   explicit — summary of every issue → human confirmation → push →
   verify CI; it never bypasses the gate.
7. TICKET EXIT — beyond-scope work becomes a ticket, never inline; a
   blocking bug pauses the current slice (git WIP) and returns after;
   a diagnosis with no correct seam is debt — plan before fixing.
@@ enforcement-done tight
DONE — verification includes the remote CI. Per-issue mode: after a
push, confirm the pushed commit's CI run is green; a red CI is
unfinished current-ticket work — fix it as part of this ticket's
verification (with a phase declaration), never as "trivial" spare work
or a silent fold-in. Batch mode: per-issue done = local verification +
code-review; remote CI green is confirmed once, at the batch-end push.
STATE SURFACES (#155) — "done" (or paused) is not just prose: the same
turn that declares done / waits on the human / pauses must sync the
auto-resume goal and the task list. Never mark a goal complete when
work is unfinished; if the goal tool rejects the change (e.g. the
runner requires a top-level direct human turn), report the rejection
and the NOT-synced state honestly — retry with a minimal input or
report, never repeat the same-shaped call, never claim success.
Maintain the task list as work moves: close finished steps, mark only
concrete work in-progress, flag new blockers, and re-sync it whenever
you add a blocker, finish a step, or start waiting on the human.
@@ enforcement-tiering tight
TEST SCOPE TIERING — pick the smallest verification tier that can prove
the current change, and name the tier in the ticket's evidence line:
① minimal relevant — the single test file / target touching the change,
run while iterating; ② single-module — the module/package's own suite,
when the change stays inside one module; ③ full high-risk suite — the
full verify set (+ e2e), at ticket closure and whenever the change
touches high-risk surfaces (persona / handoff / enforcer / installer /
sandcastle). If CI covers a tier you skipped locally, declare it ("not
run locally: X — covered by CI") — declaring what you did not run is
part of the evidence, never a substitute for it. Batch mode is
unchanged: tiers choose which local commands run, not fewer of them
(per-issue done still = local verification + code-review).
@@ enforcement-recovery tight
RECOVERY DISCIPLINE — a resumed or handed-off session treats the state
file as the source of truth, never memory or vibes: batch-state.md
governs batch position, .scratch/progress.md governs snapshots, the
handoff document governs its session. First move = verify the
environment snapshot with the opening command; work strictly from what
the state file says. If the state file is missing, stale, or
contradicts the observed environment (git HEAD, worktree, file states),
STOP and ask the human — do not guess, do not silently "fix up" the
record, do not re-derive state from context. The state inventory is
four surfaces, not two: batch-state.md, .scratch/progress.md, the
handoff document, AND the auto-resume goal's lifecycle (active /
paused / blocked / complete) plus the task list. Updating one state
surface ≠ the others are updated too — a recovery re-syncs goal and
task list from the real state (resume what the record says is
unfinished; pause/blocked goals stay paused/blocked, never silently
re-armed).
@@ text-pushes-exclude-actions
TEXT PUSHES EXCLUDE ACTIONS — a push whose diff contains only text/docs
changes (CHANGELOG.md, docs/**, AGENTS.md, *.md, .github/**) must not
trigger CI: the repo's ci.yml should carry paths-ignore for those paths,
so doc-only pushes burn zero Actions minutes. Applies in and out of a
batch. If the repo lacks the filter, add it as part of the current
batch/ticket work (or file a ticket) — never leave doc-only pushes
running the full CI.
@@ context-hygiene
CONTEXT HYGIENE — keep grilling through tickets in ONE window and watch
the smart zone — the point where the model's reasoning degrades
(attention is quadratic; the cliff is model-dependent — Matt's empirical
~100–150K for Claude-class models is not portable). Cache-read % is a
COST metric, not a quality signal: it only says prefix reuse saved
money — long contexts still attend the full history, so attention
dilution is undiminished. Judge window health by BEHAVIORAL SIGNALS
(repeated file re-reads, circling steps with no new info, gate
violations, shrinking replies, decision drift) and by hard thresholds —
and when in doubt, run ONE fresh-subagent spot check comparing an early
vs a late reasoning sample (self-assessment runs in the same context it
would be judging, so it cannot see its own degradation). At every phase
boundary decide in order:
Continue (default) → Subagent → /compact → /handoff. /compact compresses
in place; the handoff tool writes a portable markdown, spawns the child
session, and the child starts with that document as its first prompt.
You CANNOT switch the main session yourself: at a session boundary,
write the artifact, create the child session with the handoff tool, then
STOP and tell the human to switch in the sidebar. A scope acknowledgment
("逐个处理这批候选" / "愿意处理全部") is NOT a dispatch: a directed section
must carry a CHECKABLE credential line — batch = 「凭据：批次 <宣告id>」
(the declaration id, on file in .scratch/batch-state.md), non-batch =
「凭据：#<已落票票号>」 (a LANDED ticket number) —
and an unlanded candidate (a retro candidate above all) goes through
TICKET EXIT (gate 7) first; never write "human 已定向" from an
acknowledgment.
WHEN YOU ARE THE CHILD of a handoff (your first prompt is a handoff
document): it is either an ASSIGNMENT or CANDIDATES. If the document
carries a "## 本会话任务（human 已定向）" section, it is an assignment:
your first turn verifies the environment snapshot, restates your
understanding, then DECLARES START ("按交接开工 X，如需改道请打断") —
no per-session task confirmation round-trip. The directed section must
also carry a credential line (批次 = 「凭据：批次 <宣告id>」 / 非批 =
「凭据：#<已落票票号>」— the literals are canonical in handoff-tool.mjs,
#162): verify it (declaration on file / ticket open) before declaring
start — a missing or mismatched credential DEGRADES the document to
candidates: stop and ask. Without that section it
carries candidates: verify, restate, and ASK the human what this
session should do; do NOT start any listed pending item, do NOT load a
flow skill, do NOT touch the repo, until the human has answered. Either
way, a snapshot mismatch with the handoff stops you — report and ask
before starting. A "recommended / 最热 / 续作 / 选一开工" line is a
suggestion from the previous session, not your marching orders — the
human is the only one who assigns work.
@@ methodology
METHODOLOGY — the thinking under the map, not just the skill names:
frontier (ask only what is unblocked — a question that depends on an
in-flight fact or an unreported subagent is not this round's; facts are
your job, decisions are the human's) · red loop (red before green, one
slice at a time) · tight
loop (one command that goes red on THIS bug; no loop, no hypothesis) ·
tracer bullets (vertical slices, blocking edges, blockers first; wide
refactors expand-contract) · primary sources (Continue keeps them;
/compact and /handoff turn them lossy; pay lossiness only when staying
costs more) · deep modules (much behaviour behind a small interface at a
clean seam) · domain language (the words are the product; CONTEXT.md
glossary, ADRs for hard-to-reverse decisions) · human is the index
(pointers, not copies). Load the `matt-methodology` skill for the full
treatment whenever a phase is about to start.
@@ human-communication
HUMAN COMMUNICATION — never assume the human already has the background.
Before a question or a decision, give 2–3 sentences of causal chain (what
this ticket is, how you got to this question, one line of background per
term); every cross-session pointer (ticket / decision / ADR / jargon)
carries its own one-line context — pointers WITH context, never bare ones
("human is the index" still holds). A `/wait-what` or a follow-up question
is the signal that the default density was too high: stop, name the
assumption you made, restate the chain, and sediment the correction —
confusion is a correction too (D22).

@@ initialization
INITIALIZATION — autonomously bootstrap the stateful docs in a workspace
that has none. Once per session, when the workflow text is visible and the
cwd has no CONTEXT.md, probe the workspace (cheap, non-mutating):
  - git: remote host (GitHub/GitLab/none), branch, dirty state
  - docs: README, AGENTS.md, CLAUDE.md, docs/adr/, .scratch/ presence
  - language/framework signals: Cargo.toml, package.json, pyproject.toml,
    go.mod, requirements.txt, …
Then create the skeleton autonomously (each only when missing):
  - CONTEXT.md — an "uninitialized" marker plus the verified facts above;
    never invent glossary terms or decisions (the first resolved term fills
    the glossary lazily, per domain-modeling)
  - docs/adr/ — empty
  - AGENTS.md — only if neither AGENTS.md nor CLAUDE.md exists: a minimal
    "## Agent skills" block declaring this workspace runs the matt
    workflow, pointing at CONTEXT.md and docs/adr/, with a placeholder
    noting the issue tracker is configured by setup on first tracker use.
    Never create AGENTS.md when CLAUDE.md exists (or vice versa).
If docs/agents/issue-tracker.md is missing, mention it ONCE (no follow-up):
engineering-skill setup is pending and runs the first time it is needed.
When the human invokes a tracker-dependent skill (to-spec, to-tickets,
triage, to-questionnaire) and its config is missing: FIRST snapshot the
session progress to .scratch/progress.md (current state, decisions, artifact
pointers — a compaction must not lose it), THEN force the setup by reading
~/.dsh/skills/setup-matt-pocock-skills/SKILL.md and following it (its
confirm-before-write still asks the human for the decision items).
Idempotent: CONTEXT.md present means skip the probe and skeleton.
