## B 组（批内 auto-handoff 接力链）——三链，每链两跳

链形状：hop1 做票 A（slugify）→ 写定向交接文档（handoff_tool 五节形状）+ 更新
`.eval/batch-state.md` → 结束；runner 机械复核产物清单 → 把交接文档**原文**作为 hop2
首条 prompt（fresh + 文档，零继承历史）→ hop2 承接票 B（slug-cli，复用票 A 导出）。

  batch-state 2 分 + human 交互 **0** 次）：**chain1 pass、chain2 pass、chain3 fail**
  （chain3 三项达标，唯 hop2 有 1 次批末 `ask_user_question` 阻塞问询——按自定判据计 fail，

  核账（审计位）」**。另记一处 runner 侧事实：chain3 hop2 的 turn 是被 **45 分钟超时截断**的

  应答通道，超时收场；票 B 交付物（`825ce5a` + batch-state 更新）在问询**之前**已完整落盘，

### 结论的携带项（给 L2 提案供 human 拍板）

1. **编排唤醒是第一依赖，不是优化项**。chain1 首跑（runner 加宽限/nudge 之前）hop1 在等
   code-review 并行子代理时结束 turn，交接文档未产出 → 接力在 hop1 断链；A 组 run3 首跑
   同模式。runner 补「turn/end 后 6 分钟宽限 + 交付就绪判据未满足则 1 次 nudge」（判据：
   A 组 = 提交 + evidence/green.txt + .eval/{delivery-comment,decision-gate}.md；hop1 =
   交接文档在盘；hop2 = 有新提交——runner `deliverableReady`，注意 nudge 只覆盖这些面，
   不是任意口径的「交付未齐」）后全部恢复。三链最终 nudge 计数 0/0/0（chain3 的 1 次交互
   是会话主动 ask，不是 nudge）——即：**带唤醒兜底时全自动成立；没有唤醒机制时自动接力
   不可靠**（两次实测断链都卡在同一处）。桌面端今天由 human 兜底这个角色；L2 提案必须把
   它变成机制（subagent settle → 父会话 inbox 唤醒，或编排器轮询 subagentCatalog 补
   prompt——本轮 nudge 即后者的最小实现）。
2. **批末收尾是 residual human 交互点**：chain3 hop2 在 push 步（票面禁 push + 无 remote）
   主动 `ask_user_question` 等应答，被 runner 的 45 分钟 turn 超时截断（见链判定节）——
   会话没有做错：push/关票属 D21 外部动作门，它停下问人是对的行为；错的是**编排没有
   应答通道**。L2 的「全自动」边界大概率应画在**收尾步**（交付全自动、收尾留人工确认 +
   编排必须能转达问答），这与 #101 的 D21 拍板一致。
3. **证据强度有限**：N=3、票小（slugify 级）、单机单模型、失真率 0 可能是任务太小所致
   （票 B 只需一个导入名）。失真率指标在三链上都没有被真正压到过——值得开 ≠ 已被证伪
   失真风险；L2 提案里的批末异步审计位应保留。

## 沙箱边界与偏差披露（AC③④）

1. **tracker 往返的写 leg 是模拟的**：A 组会话真实读了 #50（gh issue view，读 leg 真），
   但「往」leg（交付评论/改标签/关票）按沙箱纪律改为落盘 `.eval/delivery-comment.md`。
   依据：D21 外部动作门（建 eval 靶票属外部动作，自主批内无确认通道）。会话在两个门上的
   行为（拒写 + 落盘 + 声明理由）本身是评测对象且三跑一致正确。
2. **无人值守下必须 `DSH_PERMISSION_MODE=danger-full-access`**（approval:'never'），
   否则工具调用卡审批（实测）。隔离面 = 每跑独立 mkdtemp sandbox + 任务明令禁 push/禁
   tracker 写；真实外部动作仍算 hard violation。`node --test` EPERM（#38 观察项）本轮
   **未出现**：preset 会话用 pwsh 工具跑 `node --test`，三组九跑无一命中——按 #38 口径
   记为「本轮未复现」，非「已修复」。
3. **runner 两处缺陷（实施期间发现，如实记）**：① 首版轮询用 `projections.running`，
   turn 进行中即误判完成（run1 首跑 outTokens=672 即退出）→ 改 page 事件流 `turn/end`
   判据；② B 分支 `checkManifest` 正则不剥 markdown 反引号 → chain3 的 3 条清单被判 0 条
   （`manifest-check.json` 为 0 是解析 bug 遗留；已用 hop2 transcript 的实测哈希离线复验
   3/3 相符，正则已修）。runner 产物缺口：B 组每跳未落 `final.diff`/`meta.json`（只有
   relay-status 汇总）——评分依据（transcript/events/快照/交接文档）仍完整，复跑者注意。
4. **失败轮如实记，不美化、不计入 N=3**：A 组 run3 首跑（未交付）与 chain1 首跑（hop1
   断链）为同因失败（子代理等待 → turn 提前结束），runner 修正后以同 label 重跑；两份
   首跑的失败形态已在正文引用。**runner 版本口径（精确版）**：三跑三链跨了三个 runner
   版本——run1/run2 产出自「page 事件流 `turn/end` 判据、**尚无**宽限/nudge」的中间版
   （meta.json 无 `nudges` 字段、目录无 `nudges.txt` 可证），run3 与三条链产出自加了
   宽限/nudge 的最终版。对结论的影响方向：run1/run2 **无编排兜底也全交付**，这使「会话
   能力面」的读数偏保守而非偏乐观；但「唤醒兜底」机制的覆盖面只有 run3 + 三链（4/5 个
   交付轮次）实测过，复跑者读 N=3 时应知道兜底路径并非全部轮次都走到。
5. **B 组接力是 runner 编排（L2 编排器视角），不是 handoff_tool 的 in-session spawn**：
   `handoff-tool.mjs` 的 `ctx.agents.create()` 路径本轮未测（out of scope：不改工作流本体）；
   L2 若拍板，spawn 路径与唤醒机制需一起补测。

## 结论（AC②）

**按 rubric 字面 N=3 = 2/3 →「可开，但需保留每跳核账（审计位）」**：接力协议本身（定向
交接文档 + 起手机械校验 + batch-state 逐跳保真）在三链上零失真、零接力失败，两链 human
交互 0 次；chain3 因 1 次批末问询按自定判据 fail，且该问询被 45 分钟超时截断——恰好划出
「全自动」的边界：交付面三链全过，收尾面（push/关票属 D21 门）天然需要 human 在环。开
L2 的条件是提案同时包含（a）子代理落定唤醒机制（无它则两次实测断链会复现）、（b）批末
收尾的人工确认位 + 编排应答通道（与 D21 一致）、（c）批末异步审计位（失真风险未被真正
压测）。拍板在 human。
