# 需求守恒正反样例集

> 本文件是匿名合成面：不含真实票号（判据出处见 `docs/agents/issue-tracker.md`
> 「需求守恒与接线移交」节与复核 brief §2 的 5d 条）。

**匿名合成声明**：全部样例为合成场景，票号一律 `#<n>` 占位——不含任何私仓票面、业务数据或
本机环境信息。判据本体在 `docs/agents/issue-tracker.md`「需求守恒与接线移交」节；本文件只供
**对照演训**：分诊 / 拆票会话照判据自测，Spec 复核（`docs/code-review-brief.md` §2 的 5d 条）
照「关票结论 vs 映射」逐例核对。样例的语义判断由评审承担，机械守卫
（`tests/verify-requirement-conservation.mjs`）只钉文本送达与入口在场，不判逐例语义。

每例走通四步：**批准要求 → 拆票 → 实施证据 → 关票结论**，并给出判定与责任归属。

## 正例

### P1 双向承接（合格）

- **批准要求**：R1「导出功能支持 CSV 与 JSON 两种格式」。
- **拆票**：票 A（AC1：CSV 导出可用，含格式合法性单测）；票 B（AC2 明确写「承接 R1 的
  JSON 导出半边：JSON 序列化与下载链路可用」，并回指 R1）。两张票都在 R1 拆票时**已存在**。
- **实施证据**：A 交 CSV 单测 + 手动导出读数（命令 + 退出码）；B 交 JSON 单测 + 下载链路
  读数。A 的关票结论只声称「R1 的 CSV 半边兑现」，未声称 R1 全部兑现。
- **关票结论**：R1 的去向映射 = A 的 AC1 + B 的 AC2 两半合计；B 关票后映射里 R1 才整体
  兑现，能力结论挂在 B 的验证证据上。
- **判定**：合格。发送侧指了接收票，接收侧 AC 承接了同一要求，两侧证据合计覆盖 R1。
- **责任归属**：拆票会话保证 B 的 AC 真承接（不是只挂依赖边）；A 关票时只对自己那半声称；
  收口复核验证两半拼起来确是 R1 全文。

### P2 明确获准取消（合格）

- **批准要求**：R2「历史数据一键迁移」。
- **拆票**：票 C 承接 R2 全文。
- **实施证据**：C 实施中发现迁移语义与既有只读快照契约冲突，**任何实现都要改契约**——
  这是范围扩张级决策。实施者停下（gate 3 的 L2），带前因后果提问 human：冲突事实、两条路
  （改契约 / 取消 R2）各自的代价。
- **关票结论**：human 拍板取消 R2，授权记录写进票面评论；C 的关票结论把 R2 的去向标为
  「获明确授权的目标变更」，R2 原文保留**未兑现**状态（由授权关闭，不是"顺路做完"）。
- **判定**：合格。取消不是实施者自判的，是 human 的 L2 拍板且有可回读记录。
- **责任归属**：实施者只能上报不能自行取消；human 是唯一取消通道；关票会话负责把授权
  记录与「未兑现」状态写清楚。

## 反例

### F1 旧语义回流（不合格）

- **批准要求**：R3「同步等待任务完成后返回结果」。
- **拆票**：票 D 的 AC 写成了「提交任务后异步轮询」——语义已与 R3 不同，但没有任何授权
  记录。
- **实施证据**：D 的轮询实现全绿（命令 + 退出码都在）。
- **关票结论**：声称「R3 兑现」。
- **判定**：**不合格**。目标在拆票面被静默改写：同步改异步是目标变更，属于 gate 3 恒 L2，
  没有授权记录 = 旧语义回流。绿灯只证明「代码符合改过的 AC」，不证明「AC 符合批准要求」。
- **责任归属**：拆票会话（要么照批准语义写 AC，要么停下来 L2 提问）；Spec 复核回溯权威
  授权结论对照时本应抓住——只对照缩窄后的 AC 会漏。

### F2 消费票漏建（不合格）

- **批准要求**：R4「事件写入端发布变更，消费端能读到」。
- **拆票**：票 E 只建了写入端（AC：发布事件可用）；消费端在票面写「后续由某票处理」，
  但那张票**从未建**。
- **实施证据**：E 的发布端测试全绿。
- **关票结论**：声称「R4 交付」。
- **判定**：**不合格**。接收票不存在，移交不成立，R4 的消费半边无人承接——R4 整条保持
  未完成状态。
- **责任归属**：E 关票时应跑一遍去向映射：三值无一成立（消费半边既不在本票、也没有已存在
  的承接票、更没有授权变更）→ 不得声称兑现；正确动作是 TICKET EXIT 把消费端立成票（只建
  不关）并保留 R4 未完成状态。

### F3 单方移交（不合格）

- **批准要求**：R5「配置项支持环境变量覆盖」。
- **拆票**：票 F（解析层）；票 G（已存在，AC 只写了「重载配置文件」）。F 的票面写
  「环境变量覆盖移交 G 处理」。
- **实施证据**：F 的解析层测试绿。
- **关票结论**：F 声称「R5 已移交，本票完成」。
- **判定**：**不合格**。G 存在，但 G 的 AC 没有承接 R5——**接收侧未承接 = 移交不存在**，
  单方移交不算数，R5 仍由 F 负责。
- **责任归属**：拆票会话（建 G 时就该把 R5 写进 G 的 AC，或补一张承接票）；F 关票时的
  映射核对应查出「接收票存在但未承接」；Spec 复核读两张票的 AC 交叉验证。

### F4 披露代替交付（不合格）

- **批准要求**：R6「批量接口单请求上限 100 条」。
- **拆票**：票 H 承接 R6。
- **实施证据**：H 实现了上限 1000 条的版本（实现不满足批准值），并在批末总结里写
  「已向相关方披露上限为 1000」。
- **关票结论**：R6 标记「已处理（已披露限制）」。
- **判定**：**不合格**。披露不是三值去向之一：既未兑现、也没有承接票、更没有 human 授权
  改目标——R6 保持未完成状态，披露动作不免除交付义务。
- **责任归属**：关票会话（要么实现批准值，要么 L2 提问 human 改目标并留授权记录，要么
  立承接票）；批末收口卡把「已披露」当 done 一并是失败。

### F5 两端各自通过但连接未验证（不合格）

- **批准要求**：R7「用户在界面上能看到账户余额」。
- **拆票**：票 I（后端：余额查询接口，AC = 接口返回余额字段）；票 J（前端：余额展示，
  AC = 组件渲染余额文本）。J 在依赖边上排在 I 之后。
- **实施证据**：I 的接口单测绿；J 的组件测试绿——但没有任何证据跑过「组件经真实接口拿到
  余额」这条链。
- **关票结论**：I、J 各自关闭，结论声称「R7 兑现」。
- **判定**：**不合格**。排程先后（J 在 I 后）不是功能连接已验证；两半各自绿不等于整条能力
  绿——R7 的能力结论必须有连接面证据（哪怕一条端到端读数）。
- **责任归属**：接收票 J（连接验证是接收侧 AC 证据的一部分，拆票时就该写进 J 的 AC）；
  收口复核（Spec 轴对照映射时应报「连接未验证」，不能被子票全关骗过）。
